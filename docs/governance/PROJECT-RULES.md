# RADAR 项目研发规约总则

## 架构与依赖

RADAR 是模块化单体。业务模块独立拥有业务规则、公开契约、数据写入权和测试；`platform` 提供认证、审计、附件、持久化及通知等基础能力；`shared` 仅放稳定 DTO 和无业务语义的纯工具。

- 模块间默认禁止访问内部实现、路由、仓储、前端私有组件和表；只能依赖 `modules.yaml` 登记的公开入口。
- 公开入口固定为模块的 `index.js` 与 `contracts/**`。新增公共能力优先新增语义明确的方法，保持旧方法语义不变，禁止以 `V2`、`New` 规避设计。
- `requirements` 与 `tickets` 是独立模块，分别拥有自己的字段、编号与写入权；后续链路通过各自公开契约协作，不引入统一业务写模块。
- 业务路由只适配 HTTP；业务编排放 `application`，数据访问放 `infrastructure`，跨模块 DTO 放 `contracts`。

## 数据、接口与迁移

- 受保护接口必须执行服务端身份、RBAC、数据范围和实体级授权。前端权限只改善体验。
- 所有写操作应接入统一审计；附件只能经附件平台能力访问，业务模块不得暴露或直接拼接存储路径。
- API 保持 `{ code, data, message }`；内部与外部接口均使用固定 DTO 和服务端字段白名单。
- SQLite 与 TDSQL/MySQL 8 均是正式兼容目标。迁移只追加、不改历史；每个 schema 变更必须提供两端等价脚本、兼容说明和回退/补偿方案。
- `req_code` 是历史列名；跨模块新契约明确使用 `workItemCode` 并同时标注来源类型，不改变历史 API 的兼容行为。

## 外网与集成

外网辅助入口当前不实施。未来若启用，只能作为内网已存在能力的非涉密子集：固定 DTO、字段白名单、动作白名单、独立认证和全量审计（用户、IP、路由、业务编号、结果、trace ID）。不得通过前端裁剪内网完整响应实现保密。

## 质量与变更

每项变更必须有需求、任务范围、测试证据与回退说明。普通模块变更至少覆盖正常、异常、权限与边界；公共能力、迁移、认证、审计、附件、外网与发布属于重要或高风险变更，需额外 Owner 审批。可自动化的规则必须进入 CI。
