# RADAR 项目研发规约总则

## 需求准入与文档先行

- 需求编号仅在开发者命名空间内递增。全局唯一需求引用为 `<开发者账号>/REQ-YYYYMMDD-NNN`，目录固定为 `docs/requirements/<开发者账号>/<REQ-YYYYMMDD-NNN>/`；`requirement_id` 保留不含开发者的本地编号，`requirement.md` 的 `requirement_ref`、标题、任务范围 `requirement.ref`、目录和分支前缀必须一致，所有跨目录、分支、PR、提交和报告引用必须使用完整 `requirement_ref`。
- 任何实现改动前，必须完成并确认状态为 `ready` 的 `requirement.md`、完整 `ai-task-scope.yaml` 和需求影响分析；需求、范围、模块、验收或影响实现的结论存在未决项时，不得开始编码。
- 影响分析识别出的相关文档必须先完成并与需求一致，再实施代码改动。适用文档包括输入项/交付件配置范围与标识、公开契约与兼容说明、数据库迁移与历史数据方案、权限审计附件外网影响、测试验收和回退说明。
- “不适用”必须写明理由；不得以代码中的硬编码、口头约定或实施后补文档替代实施前的设计结论。实施中如结论发生变化，应先更新需求及相关文档，再继续实现。

## 架构与依赖

RADAR 是模块化单体。业务模块独立拥有业务规则、公开契约、数据写入权和测试；`platform` 提供认证、审计、附件、持久化及通知等基础能力；`shared` 提供稳定 DTO、共享 UI、流程展示与无领域数据所有权的协作能力。

- 模块间默认禁止访问内部实现、路由、仓储、前端私有组件和表；只能依赖 `modules.yaml` 登记的公开入口。
- 公开入口固定为模块的 `index.js` 与 `contracts/**`。新增公共能力优先新增语义明确的方法，保持旧方法语义不变，禁止以 `V2`、`New` 规避设计。
- `requirements` 与 `tickets` 是独立模块，分别拥有自己的字段、编号与写入权；后续链路通过各自公开契约协作，不引入统一业务写模块。
- 业务路由只适配 HTTP；业务编排放 `application`，数据访问放 `infrastructure`，跨模块 DTO 放 `contracts`。
- `platform` 对其他模块只读：业务模块只能调用已登记的公开契约，不能修改、反向依赖或在其中放置业务规则。`shared` 对其他模块可读写：新增或修改共享能力必须无业务表写入权、无业务模块私有依赖，并通过 Shared Change Issue、Owner 审批和回归测试。
- 任务范围 `assignment.module` 必须是 `modules.yaml` 中一个确切的主模块键，不能以逗号拼接多个模块。跨模块需求以该主模块组织；在需求和 `public_capability_change.target_modules` 中逐项列出所有被修改模块、公开契约、直接写入原因和各 Owner 审批。写入 `settings`、`platform` 或 `shared` 的内部实现并不因 `writable_paths` 自动获准，仍须满足其模块规则和审批要求。
- 内置字段、扩展字段、交付件定义、分区布局、状态规则及其版本均归 `settings/process-configuration` 所有；参考数据、系统、投产点和编号规则归 `settings/reference-data` 所有。其他模块只可通过其公开契约读取和按授权写入配置值。
- 新增业务模块或业务页面时，必须在需求和设计阶段分析其是否包含需要填写、展示或校验的输入项，或需要提交、下载、校验的交付件；分析结论及适用范围必须写入任务范围或交付说明。
- 如上述分析存在输入项或交付件，交付时必须在 `settings/process-configuration` 新增该模块/页面的配置范围，使“系统设置 → 输入项配置”和/或“系统设置 → 交付件配置”显示对应的配置页签；不得以业务页面中的硬编码内容替代配置范围或页签。
- 凡新增或调整需要业务人员填写、展示或校验的输入项（包括新功能的输入项，以及既有模块新增的内置字段或扩展字段），必须在对应“系统设置 → 输入项配置”页签完成注册，并配置布局和必要的状态/校验规则。
- 输入项配置注册不会自动在业务页面渲染。新增业务字段时，需求和验收必须逐项确认列表列、列表筛选、详情/编辑页字段声明（内置字段使用对应 `StageBuiltinField`）以及“系统设置 → 输入项配置”四个位置是否适用并已生效；不适用时记录原因，适用项缺失即为遗漏。
- 输入项、交付件、分区或状态规则的默认定义变更必须同时覆盖新库和已有环境：新库通过默认种子创建；已有环境通过版本化、幂等的配置升级补齐缺失定义。升级只能新增或校准本次明确的缺失项，不得覆盖管理员已调整的布局、可见性、排序、必填规则或自定义定义；需求中须说明升级键、保留策略和旧库回显验证。
- 凡新增交付件或交付件模板，必须在对应“系统设置 → 交付件配置”页签完成注册，并配置状态规则和模板版本（适用时）；业务模块只能消费已注册的交付件定义。
- 新增必填输入项，或将既有输入项设为必填（包括由状态规则触发的必填）时，必须同步为该适用范围的默认种子数据和静态 mock 数据填充合法值，并覆盖正常保存/提交场景；仅用于验证必填校验的负向测试数据可留空，但必须在测试中明确标识。
- mock 数据存放位置固定：默认配置及其字段/交付件定义写入 `server/src/bootstrap/seed.js`；用于本地演示和全链路验证的业务 mock 数据（含必填项值）写入 `server/scripts/mock-data.js`；仅供自动化测试使用的最小化数据写在对应 `server/test/**/*.test.js`。不得将 mock 数据写入生产迁移、附件目录或前端页面硬编码。
- 涉及上述配置注册的变更，需求、任务范围或交付说明必须列明配置项标识/版本、存量数据兼容或补录方案（如适用），并验证配置页与目标业务功能均可正常使用。

## 数据、接口与迁移

- 受保护接口必须执行服务端身份、RBAC、数据范围和实体级授权。前端权限只改善体验。
- 所有写操作应接入统一审计；附件只能经附件平台能力访问，业务模块不得暴露或直接拼接存储路径。
- API 保持 `{ code, data, message }`；内部与外部接口均使用固定 DTO 和服务端字段白名单。
- 新增或调整枚举、范围、格式、默认值或空值语义的字段，必须在需求中写明合法值、空值处理和错误结果，并在服务端创建、更新、批量导入等全部写入入口执行同一校验；前端控件仅改善体验，不能作为数据约束。除非需求明确记录兼容映射及其审计/提示，导入遇到非法值必须拒绝该行并返回字段、原值和原因，不得静默改写为默认值。
- SQLite 与 TDSQL/MySQL 8 均是正式兼容目标。迁移只追加、不改历史；每个 schema 变更必须提供两端等价脚本、兼容说明和回退/补偿方案。
- `req_code` 是历史列名；跨模块新契约明确使用 `workItemCode` 并同时标注来源类型，不改变历史 API 的兼容行为。

## 外网与集成

外网辅助入口当前不实施。未来若启用，只能作为内网已存在能力的非涉密子集：固定 DTO、字段白名单、动作白名单、独立认证和全量审计（用户、IP、路由、业务编号、结果、trace ID）。不得通过前端裁剪内网完整响应实现保密。

## 质量与变更

每项变更必须有需求、任务范围、测试证据与回退说明。普通模块变更至少覆盖正常、异常、权限与边界；公共能力、迁移、认证、审计、附件、外网与发布属于重要或高风险变更，需额外 Owner 审批。每项验收标准都要有可定位的测试用例；测试命令、筛选条件和报告必须能证明该用例实际执行，不能以未匹配功能用例的空泛通过代替验证。提交前不得保留“待实施”或空白完成记录，并须通过代码注释、格式和空白检查（包括 `git diff --check`）。可自动化的规则必须进入 CI。
