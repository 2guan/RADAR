# RADAR 需求改动示例

本文提供可直接模仿的需求、任务范围和完成报告写法，帮助 AI 和开发人员在实现前补全高频遗漏项。它不是平行规则来源：架构、配置、数据和安全规则以 [项目研发规约](../governance/PROJECT-RULES.md) 为准；AI 执行要求以 [AI Coding 规约](../governance/AI-CODING-RULES.md) 为准；分支和 PR 以 [GitHub 协作规约](../governance/GITHUB-RULES.md) 为准。

所有编号、字段、人员和数据均为虚构示例。全局需求引用使用 `<开发者账号>/REQ-YYYYMMDD-NNN`；例如 `hengguan/REQ-20260730-001` 的目录为 `docs/requirements/hengguan/REQ-20260730-001/`。

## 使用方式

1. 选择与当前需求最接近的案例，而不是机械复制所有步骤。
2. 在 `requirement.md` 的“5A. 配置与交付影响分析”中逐项填写适用结论。
3. 将示例中的模块、配置范围、字段标识、测试和回退方式替换为当前任务的真实设计。
4. 找不到匹配案例时，先根据正式规约记录分析结论，并完成相关文档后再开始实现。

## 示例零：文档先行的需求准入

**目标**：开发“工单退回分析”前，先完成需求和相关文档，而不是由代码实现反推规则。

### 实施前必须完成

```text
1. requirement.md：目标、使用者、状态规则、权限、验收和明确不做项完整。
2. ai-task-scope.yaml：`requirement_ref`、目标模块、正确分支、可写路径、风险和测试完整。
3. 影响分析：确认输入项、交付件、公开契约、数据库、权限/审计/附件/外网的适用结论。
4. 相关文档：适用时先完成配置范围与字段标识、接口兼容说明、迁移方案、测试与回退说明。
5. 准入：无影响实现的未决项，需求状态为 ready，才开始修改代码。
```

### 错误做法

- 先在工单页面加“退回”按钮，再讨论哪些角色可操作、能退回到哪个状态。
- 先增加必填字段，完成后才补系统设置中的字段注册。
- 先写迁移或 API，再补历史数据兼容、错误响应和回退方案。

### 正确记录

```md
## 0. AI 执行约束

- 本需求的状态流转、`ticket:return` 权限、审计事件、失败保持状态已写入需求并无未决项。
- 不新增输入项、交付件、数据库字段或公共契约；第 5A 节均已记录不适用原因。
- 需求状态为 `ready` 后才开始模块实现。
```

## 场景索引

| 场景 | 重点检查 |
| --- | --- |
| 新增或调整输入项 | 系统设置注册、布局、状态规则、种子、mock、正常保存测试 |
| 新增交付件或模板 | 交付件定义、状态规则、模板版本、附件权限 |
| 只读派生展示 | 明确为什么不注册输入项，不改变既有写入语义 |
| 跨模块读取或聚合 | 公开契约、批量读取、数据来源类型、兼容性 |
| 新 API 或写操作 | DTO 白名单、RBAC、实体级授权、审计、异常路径 |
| 数据库结构变更 | SQLite 与 TDSQL/MySQL 8 迁移、兼容、补偿或回退 |
| 导入导出 | 字段白名单、校验、错误反馈、权限和脱敏 |
| UI 与共享组件 | 复用 `DataTable`、`StatusBadge`、`FilterPanel` 等能力，不复制实现 |
| 分支、提交与 PR | 需求编号、分支名、任务范围、单需求提交边界 |

## 示例一：开发任务新增必填输入项

**目标**：在开发任务中新增“变更原因”字段，用户在提交“待测试”前必须填写。

### 需求范围写法

```md
### 本次要做

1. 在开发任务页面展示并编辑 `change_reason`。
2. 在 `settings/process-configuration` 的 `development.task` 范围注册该输入项，配置默认布局和“待测试”状态下必填规则。
3. 补齐默认种子数据、业务 mock 数据及正常保存/提交测试。
```

### 5A 分析写法

| 项目 | 适用？ | 结论、标识与验证证据 |
| --- | --- | --- |
| 输入项配置注册 | 是 | 范围 `development.task`，字段 `change_reason`；在“待测试”状态设为必填，并配置在基本信息区 |
| 交付件配置注册 | 否 | 不新增提交、下载或校验的交付件 |
| 种子与 mock 数据 | 是 | `seed.js` 和 `mock-data.js` 的开发任务均填入脱敏值；正常提交测试覆盖合法值 |
| 公共能力或跨模块契约 | 否 | 字段归开发模块自身所有 |
| 数据库与历史数据 | 是 | 新列追加 SQLite 与 TDSQL/MySQL 8 迁移；存量记录允许为空，仅在进入目标状态时校验 |
| 权限、审计、附件、外网 | 是 | 沿用开发任务写权限和统一审计；无附件、外网影响 |

### 常见遗漏

- 只在前端表单增加输入框，未在系统设置注册配置范围。
- 将字段硬编码为始终必填，忽略“仅进入待测试时必填”的状态规则。
- 新增必填后未补种子/mock，导致本地演示或正常回归失败。

### 完成报告写法

```md
- 配置与交付影响落实：已在 `development.task` 注册 `change_reason`，配置基本信息布局和“待测试”必填规则；种子、mock 与正常提交测试均使用脱敏合法值。未新增交付件。
- 发布验证：以存量开发任务编辑、提交至待测试、系统设置配置页回显三个场景验证。
```

## 示例二：新增交付件模板

**目标**：投产审批新增“回退预案”模板，审批通过前必须上传。

### 5A 分析写法

| 项目 | 适用？ | 结论、标识与验证证据 |
| --- | --- | --- |
| 输入项配置注册 | 否 | 不新增业务填写字段 |
| 交付件配置注册 | 是 | 范围 `release.approval`，交付件 `rollback_plan`；配置“待评审”状态校验和模板版本 `v1` |
| 种子与 mock 数据 | 是 | 默认交付件定义、模板元数据与演示审批记录均补齐 |
| 公共能力或跨模块契约 | 否 | 消费既有附件平台公开能力 |
| 数据库与历史数据 | 否 | 复用配置和附件现有数据模型 |
| 权限、审计、附件、外网 | 是 | 上传、下载和删除沿用附件实体权限与审计；无外网开放 |

### 常见遗漏

- 只在审批页加入上传控件，未注册交付件定义或模板版本。
- 直接拼接存储路径而不是使用附件平台能力。
- 只验证上传成功，未验证目标状态下缺失交付件会被服务端拒绝。

## 示例三：只读派生任务状态展示

**目标**：在列表显示全链路“任务状态”，不新增用户输入或数据库字段。

### 5A 分析写法

| 项目 | 适用？ | 结论、标识与验证证据 |
| --- | --- | --- |
| 输入项配置注册 | 否 | `task_status` 是服务端读取时派生的只读字段，不可填写、保存或校验 |
| 交付件配置注册 | 否 | 不涉及交付件 |
| 种子与 mock 数据 | 否 | 不新增必填配置；现有测试数据已可计算状态 |
| 公共能力或跨模块契约 | 是 | 新增只读批量生命周期状态聚合契约，保持原列表字段语义不变 |
| 数据库与历史数据 | 否 | 不持久化派生字段 |
| 权限、审计、附件、外网 | 是 | 沿用列表查看 RBAC；无写操作和新增审计 |

### 常见遗漏

- 因为字段在页面可见，就误把它注册为用户输入项。
- 在多个页面各自计算状态，导致口径漂移。
- 将派生值写回业务表，意外改变原状态语义。

## 示例四：跨模块只读聚合

**目标**：版本概览批量显示关联需求和工单的负责人。

### 正确做法

- 在目标模块 `index.js` 或 `contracts/**` 增加语义明确的批量只读方法，例如 `resolveWorkItemOwners`。
- 调用方按当前页编号批量读取，返回 `workItemCode` 与来源类型，避免逐行查询和直接访问他人表。
- 在任务范围中写明公共契约、兼容性和回归测试；不新增统一业务写模块。

### 常见遗漏

- 概览模块直接导入需求/工单的仓储或 SQL。
- 仅按编号聚合而不携带来源类型，导致需求和工单编号语义混淆。
- 为图省事在每行循环中调用跨模块查询。

## 示例五：新增受保护写操作

**目标**：为工单增加“退回分析”动作。

### 需求与验证要点

- 明确允许执行动作的角色、数据范围、实体状态前置条件和失败提示。
- 路由只适配 HTTP；业务动作放在模块应用层；请求和更新字段使用服务端 DTO/白名单。
- 服务端执行身份、RBAC、数据范围、实体级授权和状态校验；写入统一审计。
- 验收至少覆盖正常、未登录、无权限、跨数据范围、错误状态和重复操作。

### 5A 分析写法

| 项目 | 适用？ | 结论、标识与验证证据 |
| --- | --- | --- |
| 输入项配置注册 | 否 | 仅变更状态，不新增填写或展示字段 |
| 公共能力或跨模块契约 | 否 | 动作只属于工单模块 |
| 权限、审计、附件、外网 | 是 | 新增服务端动作权限、状态校验和审计事件；无附件、外网影响 |

## 示例六：数据库结构变更

**目标**：为测试任务增加可检索的“计划完成日期”。

### 正确做法

- 追加 SQLite 与 TDSQL/MySQL 8 的等价迁移，不改写已发布迁移。
- 说明现有记录的默认值、空值语义、查询排序兼容性和回退/补偿方式。
- 在 API DTO、服务端字段白名单、页面格式化和测试数据中同步处理。
- 验证两种数据库下的迁移、创建、查询、排序和回退路径。

### 常见遗漏

- 只增加 SQLite 迁移，或直接修改历史迁移文件。
- 前端传入字段但服务端白名单未放行，或排序字段未白名单化。
- 将日期格式化逻辑散落在多个页面。

## 示例七：导入导出字段扩展

**目标**：需求导入导出增加“业务优先级”。

### 需明确的内容

- 导入模板列名、可接受字典值、错误行反馈和空值策略。
- 导出字段是否受数据范围、脱敏和权限影响。
- 使用既有导入导出平台能力，不在业务页自行解析 Excel 或生成下载文件。
- 如果该字段可填写或校验，按示例一完成输入项配置分析；如果只是已有字段的导入映射，说明配置不适用原因。

## 示例八：页面改版或共享组件复用

**目标**：将测试任务列表改为展示额外状态标签。

### 正确做法

- 列表优先使用 `DataTable`；状态使用 `StatusBadge`；筛选使用 `FilterPanel`。
- 先确认新增内容是只读派生展示、既有字段展示还是新的业务输入项，并分别记录配置影响结论。
- 验证加载、空态、失败、无权限、窄屏卡片和明暗主题；颜色不作为唯一信息来源。

### 常见遗漏

- 为单页复制状态组件或表格实现，造成视觉与行为不一致。
- 因为只改前端而跳过字段来源、权限和配置影响分析。

## 示例九：分支、提交与 PR

### 正确示例

```text
需求引用：hengguan/REQ-20260730-003
需求目录：docs/requirements/hengguan/REQ-20260730-003/
分支：hengguan/REQ-20260730-003-add-dev-change-reason
任务范围 assignment.branch：hengguan/REQ-20260730-003-add-dev-change-reason
PR 标题：feat(hengguan/REQ-20260730-003): add development change reason
```

### 常见错误

| 错误写法 | 问题 | 正确处理 |
| --- | --- | --- |
| `feature/add-field` | 缺少开发者和需求编号 | 使用完整规范分支名 |
| `hengguan/REQ-20260730-002-add-field` | 与完整需求引用或需求目录编号不一致 | 统一开发者、需求、分支、任务范围和 PR 编号 |
| 在另一需求的分支继续修改 | 会混入不相关提交和范围 | 切换或新建当前需求分支后再修改 |
| 直接推送 `main` | 绕过常规 PR 流程 | 仅在需求和任务范围均明确批准例外时执行 |

## 示例十：完成报告的简洁模板

```md
## 完成记录

- 修改文件与范围一致性：仅修改 `development`、`settings/process-configuration` 及对应测试，均在任务范围允许路径内。
- 配置与交付影响落实：输入项配置适用，已注册 `development.task/change_reason` 并配置状态必填；交付件不适用；公共能力不适用；数据库迁移适用，已提供双端迁移和存量空值兼容说明；权限和审计沿用既有规则。
- 测试证据：执行前端构建、后端单元/API/RBAC、SQLite 与 TDSQL/MySQL 8 迁移验证，结果均通过。
- 已知风险：存量任务进入“待测试”前需要补填变更原因。
- 发布验证与回退：验证系统设置配置页、存量任务编辑和状态提交；如有回归，回退本需求提交，数据库列保留且允许为空。
```
