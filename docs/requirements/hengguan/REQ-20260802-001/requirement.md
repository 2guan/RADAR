# [hengguan/REQ-20260802-001] 投产申请按开发实施方自动填充实施机构

## 0. AI 执行约束

- 仅调整投产申请新增表单的实施机构默认值来源，以及完成该联动所需的 release 与 development 公开契约、接口和测试；不修改已存在投产申请的实施机构，不修改开发任务、系统主数据、流程字段配置、状态机、导入导出或数据库结构。
- `dev_task` 归 development 所有；release 不直接访问其表，必须通过 development 的 `index.js` 新增只读公开契约取得匹配开发任务的开发实施方。
- 实施机构仍由现有机构字典控制，自动填入只是可编辑默认值；创建和更新继续由 release 服务端按现有字段白名单、状态规则和审计处理。

## 1. 目标与业务价值

- 要解决的问题：投产申请新增时，选择变更系统后实施机构当前取系统主数据所属机构，可能与实际开发任务的“开发实施方”不一致。
- 预期结果：新增投产申请中，选择变更系统后，系统优先根据已关联需求/工单和该系统匹配开发任务的开发实施方自动填入实施机构；无唯一开发实施方时回退为该系统所属实施机构，用户仍可改选。
- 业务价值：让投产申请的实施归属继承实际开发承接结果，减少重复输入和后续统计、审批责任口径差异。

## 2. 使用者与场景

| 使用者 | 触发条件 | 前置条件 | 操作场景 | 完成结果 |
| --- | --- | --- | --- | --- |
| 投产申请创建人员 | 在投产申请列表点击新增 | 具有 `release_apply.create`，已关联至少一个需求/工单且存在对应开发任务 | 选择变更系统 | 实施机构自动显示唯一匹配开发任务的开发实施方，且可手工调整后保存 |

## 3. 范围

### 本次要做

1. development 新增只读公开契约：以工作项编号集合和开发实施系统编号查询 `dev_task.impl_org`，返回去空、去重后的实施方结果，不暴露开发任务其他字段。
2. release 新增受 `release_apply.create` 保护的默认值查询接口；服务端先校验关联工作项的数据范围，再调用 development 公开契约。恰有一个实施方时返回该值；无匹配或存在多个不同值时返回原因，供前端回退系统所属实施机构。
3. 投产申请编辑器仅在新增态、变更系统发生变更时调用默认值接口：先按系统所属实施机构填入，再以唯一开发实施方覆盖；保留输出/部署部门按系统主数据回填的既有行为。
4. 实施机构控件保持可编辑。无匹配或多个不同开发实施方时展示邻近字段的明确说明，并回退为系统主数据所属实施机构；系统也没有所属机构时才要求用户手工选择。
5. 选择系统后再快速切换系统或关联工作项时，过期响应不得覆盖当前系统的实施机构。

### 明确不做

1. 不为编辑态的历史投产申请重新推导或覆盖实施机构。
2. 不改变 `dev_task.impl_org`、系统所属机构、机构字典、现有投产申请持久化字段、数据库迁移、导入导出或审批流程。
3. 不在没有匹配开发任务、未关联工作项或多实施方冲突时猜测或写入默认机构。

## 4. 行为与业务规则

| 规则编号 | 触发条件 | 业务规则 | 不满足时处理 |
| --- | --- | --- | --- |
| BR-001 | 新增投产申请选择变更系统 | 以当前已关联需求/工单编号和所选系统精确匹配开发任务的 `req_code`、`impl_system`，读取非空 `impl_org` 去重集合。 | 未关联工作项或无匹配任务时不填入实施机构，提示手工选择。 |
| BR-002 | 匹配结果唯一 | 仅当去重后恰有一个开发实施方时，接口返回并由新增表单自动填入该值。自动值与手工值均可由用户修改。 | 无。 |

| BR-004 | 变更系统或关联工作项切换 | 新请求携带当前完整关联编号和系统编号；前端仅应用仍与当前选择相符的最新响应。 | 查询失败时回退系统所属机构；系统无所属机构时保持空值并提示手工选择，不阻塞手工填写。 |
| BR-005 | 查询默认值 | release 接口要求 `release_apply.create`，并复用关联工作项机构数据范围校验；development 契约只返回机构值集合。 | 无权限或关联工作项越权返回既有 `403`，前端不得泄露机构值。 |

## 6. 权限、审计与外网

- 仅具备 `release_apply.create` 的用户可请求新增态默认值；服务端对每个关联需求/工单执行既有机构数据范围校验。
- development 公开契约只返回匹配的实施机构集合，不能被前端直接调用以绕过 release 权限。
- 自动默认值读取不写审计；投产申请创建/更新继续使用既有审计。
- 不涉及附件、外网字段、外网动作或敏感信息。

## 8. 研发上下文

- 主模块为 `governance`，Owner 为 `hengguan`；本需求通过 release→development 的公开契约完成跨模块协作，受影响模块为 release、development。基准分支 `origin/main`，分支 `hengguan/REQ-20260802-001-release-apply-impl-org`。
- release 拥有投产申请表单、HTTP 适配和实体授权；development 拥有 `dev_task`，以 `server/src/modules/development/index.js` 的只读公开契约提供最小查询结果。禁止 release 直接查询开发表。
- 复用既有 `ReleaseApplyEditor`、`DictSelect`、`getWorkItem`、机构数据范围校验、`requirePerm`、API 响应信封和投产申请保存审计。
- 新接口：`POST /release-apply/implementation-org-default`，请求 `{ refCodes: string[], systemCode: string }`，响应 `{ implOrg: string | null, reason: 'resolved' | 'no_match' | 'conflict' }`，要求 `release_apply.create`。前端在 `implOrg` 为空时复用已加载的系统主数据 `org` 作为默认值。无数据库迁移、外网接口或附件变更。
- 必须执行：针对 BR/AC 的 development 契约及 release API/RBAC 测试、前端构建、UI 数据源检查、模块边界检查、代码注释检查、`git diff --check`、本地运行验证和真实浏览器新增申请路径验收。
- 风险：历史任务可能没有实施方或同系统出现多个机构；该场景回退为现有系统所属机构默认值，用户仍需确认并可手工修改。回退时回退应用即可，历史数据未被写入或迁移。
