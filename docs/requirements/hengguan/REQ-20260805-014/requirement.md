# [hengguan/REQ-20260805-014] 交付制品投产状态与审批自动完成

## 0. AI 执行约束

- 本需求仅调整投产申请的交付制品结构、受控参数、投产审批详情展示及由制品状态驱动的审批状态自动推进；不新增页面入口，不调整需求、工单、开发、测试的业务字段或状态机。
- 交付制品继续存于 `release_apply.delivery_units` 的 JSON 数组；新增键为 `artifact_release_status`，不建立平行子表或在需求/工单表写入派生状态。
- 业务模块只能通过 `settings/reference-data` 的公开入口读取、解析制品投产状态；不得访问 settings 私有实现。自动推进由服务端在同一受保护写入流程中计算并审计，不能相信客户端提交的审批状态。
- 投产审批详情允许在关联制品卡片内直接调整摆渡状态和制品投产状态；该动作归投产申请所有，必须使用 `release_apply:edit` 与申请实体数据范围校验，不能因拥有 `release:status.edit` 而越权改制品。
- 已在 `hengguan/REQ-20260805-014-artifact-release-status` 分支实施；合并前仍须由 Owner 按任务范围复核。

## 1. 目标与业务价值

- 要解决的问题：交付制品只记录摆渡状态，无法逐项确认是否已投产；投产审批详情也无法基于关联制品自动完成投产。
- 预期结果：每个交付制品在编辑态可维护独立的“制品投产状态”；管理员可在系统设置维护该状态参数；审批详情同时显示摆渡状态和制品投产状态；满足规则时审批任务自动进入“已投产”。
- 业务价值：把“介质已摆渡”和“制品已投产”明确区分，减少人工逐工单核对和遗漏状态推进。

## 2. 使用者与场景

| 使用者 | 触发条件 | 前置条件 | 操作场景 | 完成结果 |
| --- | --- | --- | --- | --- |
| 投产申请维护人 | 已提交投产申请且具有编辑权限 | 申请至少有一组交付制品 | 编辑申请中的某一制品 | 可选择并保存该制品的投产状态；新增申请不显示该控件 |
| 投产审批查看人 | 查看需求/工单在指定投产点的审批详情 | 具有投产审批查看权限 | 展开关联制品 | 每项制品按两行阅读：第一行状态摘要，第二行交付单元与投产状态 |
| 投产审批操作人 | 在审批详情核对摆渡/投产进度 | 同时具有 `release:view`、`release_apply:edit` 及对应申请数据范围 | 在关联制品卡片的两个下拉选择状态 | 仅该制品状态被保存、审计；满足规则时审批自动已投产 |
| 参数配置管理员 | 需要维护状态集合 | 具有系统设置参数配置权限 | 打开“制品投产状态”页签 | 维护受控值；初始项和默认项清晰可见 |

## 3. 范围

### 本次要做

1. 将每组 `delivery_units` 从四项扩展为五项：制品类型、交付单元名称、新版本号、摆渡状态、制品投产状态（键为 `artifact_release_status`）。
2. 新增系统设置 → 参数配置 → “制品投产状态”页签，字典分类为 `artifact_release_status`；新库和已有环境均幂等补齐“待投产、已投产、已回退、已取消”四个初始项，其中“待投产”为默认项。管理员后续可按既有字典能力维护属性值、显示值、排序和启停状态。
3. 沿用摆渡状态处理：新增投产申请时不显示制品投产状态控件，服务端将每个非空制品组写为当前字典默认值；编辑/查看既有申请时显示该受控下拉。历史 JSON 中缺少该键的制品在读取、详情、导出和条件判定中按当前默认值“待投产”兼容，不得误判为已投产。
4. 投产申请列表的“交付制品”列中，每组制品在摆渡状态标签之后紧接显示制品投产状态标签；筛选以及 Excel 模板/导入/导出同步支持该状态。结构化“交付制品”单元格新格式为“制品类型 / 交付单元名称 / 新版本号 / 摆渡状态 / 制品投产状态”。四项旧格式仍可导入，缺失第五项时填当前默认值；五项格式中非法、停用或歧义的受控值拒绝整行并返回字段、原值和原因。
5. 投产审批详情的关联制品模块改为每个制品固定双行：第一行依次显示制品类型、新版本号、摆渡状态；第二行显示可完整查看的交付单元名称和制品投产状态。两个状态在拥有 `release_apply:edit` 时均使用直接下拉选择，否则以只读状态标签显示；下拉点击不得触发申请卡片跳转，长文本、多个申请和多个制品须保持既有换行、移动端折行及无横向遮挡行为。
5.1 版本概览详情的“制品投产”模块复用同一制品 DTO，按与投产审批关联制品相同的固定双行展示：第一行制品类型、新版本号、摆渡状态；第二行交付单元名称、制品投产状态。两个状态仅展示为只读标签，不提供下拉、保存入口或额外权限。
6. 对同一需求/工单及同一申请投产点，汇总其 `release_apply_reference` 关联的全部非空交付制品。集合非空、每一项的制品投产状态均为“已投产”，且该审批任务评审状态为“评审同意”或“应急审批”时，服务端自动将该 `release_task.status` 更新为“已投产”。
7. 自动判定须在交付制品新增、编辑、导入、关联编号或申请投产点变更后，以及审批详情直接修改任一制品状态、评审状态手动调整或会签重算后执行。仅执行向“已投产”的单向自动推进；不得因后续编辑把已投产自动降级，也不得覆盖人工已取消的审批。评审同意/应急审批在制品尚未全部已投产时，继续沿用既有“待投产”语义。
8. 为字典重命名的 JSON 级联、删除引用保护、初始数据、脱敏 mock、接口和前端回归补齐 `artifact_release_status`；字典属性值/显示值解析、默认值、列表筛选、详情展示与导入导出口径一致。
9. 系统设置 → 人员配置 → 角色配置表中，角色名称列的标题和内容居中；会签职责、会签评审点的标题居中、内容左对齐，以便阅读较长的会签说明。

### 明确不做

1. 不改变投产申请、投产审批的既有 RBAC、数据范围、附件权限、会签角色或外网接口。
2. 不新增 `release_apply`、`release_task` 的表列或重写历史迁移；该字段仅为既有 JSON 数组的向后兼容扩展。新字典初始数据以新增的 SQLite 与 TDSQL/MySQL 8 配对迁移补齐。
3. 不自动将审批状态回退为“待投产”、已回退或已取消；制品状态的回退/取消仅按本需求展示和保存，审批状态的其他人工处置保持现有流程。

## 4. 行为与业务规则

| 规则编号 | 触发条件 | 业务规则 | 不满足时处理 |
| --- | --- | --- | --- |
| BR-001 | 新建投产申请 | 每个非空制品组服务端填充 `artifact_release_status` 的当前默认字典属性值；新增表单不渲染该列 | 默认项不存在或已停用时拒绝保存，提示制品投产状态默认配置不可用 |
| BR-002 | 编辑投产申请 | 每组制品显示五列；摆渡状态和制品投产状态均为受控下拉，保存属性值 | 属性值/显示值不能解析为启用字典项时拒绝保存，旧值不变 |
| BR-003 | 读取历史申请 | 缺少 `artifact_release_status` 的历史 JSON 在读取、导出、详情和聚合中按当前默认值处理 | 缺少默认项时返回明确配置错误，不将空值视作已投产 |
| BR-004 | 管理状态参数 | 初始项按“待投产、已投产、已回退、已取消”排序，待投产为默认；名称/属性值改名时级联 JSON 引用，已有引用时禁止删除 | 沿用字典 API 的权限、审计和错误包装 |
| BR-005 | 导入/导出 | 新模板、示例和导出均为五项格式；旧四项导入兼容并默认待投产 | 五项中任一受控值非法、歧义或制品格式不是四/五项时拒绝整行，反馈字段、原值、原因 |
| BR-006 | 审批详情 | 指定需求/工单和申请投产点仅展示该范围的关联申请及制品；每项严格双行：第一行为制品类型、新版本号、摆渡状态，第二行为交付单元名称、制品投产状态 | 无关联制品显示既有空态，不以空集合触发自动已投产 |
| BR-006A | 审批详情直接编辑 | 拥有 `release_apply:edit` 且通过所属申请实体授权时，摆渡状态和制品投产状态均使用 `DictSelect` 直接保存；局部 API 仅接受制品索引、两个新状态和两个期望旧状态，服务端重新读取后仅更新该项状态并保留同申请其余制品字段 | 无权限、申请不存在、制品索引失效、期望旧状态不匹配、字典项非法/停用或保存冲突时拒绝，页面保留原值并提示刷新；不得触发卡片跳转 |
| BR-007 | 制品状态或关联变化 | 针对受影响的“工作项编号 + 申请投产点”重新汇总全部关联申请的非空制品；仅全集非空且全部为已投产才满足制品条件 | 任一待投产、已回退、已取消、空值或无制品均不满足，不改审批状态 |
| BR-008 | 评审状态或会签变化 | 仅当评审状态为“评审同意”或“应急审批”且 BR-007 满足时，自动将对应 `release_task.status` 置为已投产 | 评审状态不满足时不自动已投产；保持既有评审→待投产联动，且不覆盖已取消 |
| BR-009 | 自动推进 | 状态变更由服务端事务内完成，使用触发操作人的既有审计上下文，审计中注明“关联制品全部已投产自动推进” | 任何聚合、校验或写入失败时整体请求失败或保持原状态，不产生伪成功审计 |

## 6. 权限、审计与外网

| 角色 | 查看/新增/修改/动作 | 数据范围 | 内网/外网 |
| --- | --- | --- | --- |
| 具有 `release_apply:create` 的人员 | 新增申请；不提交制品投产状态 | 沿用投产申请范围 | 内网 |
| 具有 `release_apply:edit` 的人员 | 在投产申请编辑制品投产状态；在审批详情直接编辑两个制品状态 | 沿用申请所属系统/机构范围 | 内网 |
| 具有 `release:view` 的人员 | 查看审批详情的两行制品信息；无申请编辑权时只读 | 沿用审批实体授权 | 内网 |
| 具有参数配置权限的管理员 | 管理制品投产状态字典 | 全局配置范围 | 内网 |

- 无权限处理：服务端继续执行认证、RBAC、数据范围和实体授权，返回既有 `401/403`；直接下拉仅在同时通过审批查看和申请编辑权限时启用；客户端传入制品状态不能绕过启用校验或直接写审批状态。
- 审计要求：记录申请编号、制品索引、摆渡状态/制品投产状态的旧值和新值；自动置为已投产时记录受影响审批、触发人、时间和固定原因，不因条件不满足写成功审计。
- 外网开放场景、字段、动作、附件限制与禁止项：不涉及；不得开放新外网 API 或附件访问。

## 8. 研发上下文

- 业务主模块 / Owner / 基准分支：`release` / `hengguan` / `origin/main`；因本需求同时追加 `platform/persistence` 迁移并修改多个业务模块，AI 任务范围登记主模块为 `governance`，Owner 同为 `hengguan`。实施分支为 `hengguan/REQ-20260805-014-artifact-release-status`。
- 多模块协作：`release` 负责 JSON 规范化、导入导出、申请/审批页面、审批详情和自动状态编排；`overview` 负责版本概览详情中的只读制品双行摘要；`identity-access` 负责人员列表姓名列的呈现对齐；`settings` 负责字典页签、解析公开入口和字典引用级联；`platform/persistence` 仅追加 SQLite/TDSQL 的字典初始数据迁移。Owner 均为 hengguan，合并前需其复核；不得借此修改其他平台内部实现。
- 允许与禁止修改路径：见 `ai-task-scope.yaml`。特别禁止重写历史迁移、修改生产数据、`docs/reports/` 和未列模块。
